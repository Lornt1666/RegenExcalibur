# PromptOS AutoDesign / AutoEngineer

**Status:** product architecture specification. This document does not claim licensed engineering authority or implementation completion.

## Mission

AutoDesign / AutoEngineer turns a rough user objective into a bounded, multidisciplinary project package using PromptOS routing, evidence controls, requirement traceability, professional-boundary checks, and definitive completion states.

The system is intended to answer:

> What exactly should be designed, how should it work, what disciplines must be coordinated, what evidence is required, how can it be implemented, and what still requires qualified human review?

## Core operating pipeline

```text
raw objective
    ↓
intent + constraint extraction
    ↓
domain/occupation routing
    ↓
requirements + assumptions + blockers
    ↓
alternative concept generation
    ↓
multidisciplinary design synthesis
    ↓
engineering coordination specification
    ↓
risk / safety / legal / professional review gates
    ↓
implementation blueprint
    ↓
test + evidence plan
    ↓
traceability + completion record
```

## Product modes

### AUTODESIGN

For product, software, workflow, UX/UI, architecture, creative, business, or interdisciplinary concept generation.

Required output:

1. project definition;
2. stakeholder and user model;
3. requirements;
4. constraints and non-goals;
5. concept alternatives;
6. selected concept and rationale;
7. system/product architecture;
8. interfaces and data flows where applicable;
9. usability/accessibility considerations;
10. risks and failure modes;
11. implementation blueprint;
12. tests and acceptance criteria;
13. completion state.

### AUTOENGINEER

For technically constrained work requiring engineering-style decomposition and verification.

Required output, where applicable:

1. design basis;
2. governing requirements;
3. jurisdiction and standards to verify;
4. loads/inputs/operating envelopes;
5. materials/components/technologies;
6. system boundaries;
7. interfaces;
8. tolerances and constraints;
9. calculations or calculation plan;
10. safety factors or engineering margins where appropriate;
11. failure modes;
12. verification plan;
13. inspection/testing requirements;
14. maintenance/lifecycle requirements;
15. professional-review requirements;
16. implementation sequence;
17. evidence and acceptance criteria.

AI output must never be described as sealed, stamped, permit-approved, professionally certified, or equivalent unless an appropriately authorized professional actually provides that status.

### AUTOBUILD PLAN

Converts an approved specification into an implementation work breakdown without automatically performing consequential actions.

Output:

- phases;
- dependencies;
- critical path;
- responsible roles;
- tools;
- cost/resource assumptions;
- tests;
- evidence artifacts;
- review gates;
- rollback/recovery;
- terminal condition.

### AUTOAUDIT

Inspects an existing project, design, prompt, specification, or implementation package for:

- missing requirements;
- contradictions;
- unverified assumptions;
- safety gaps;
- tool/capability mismatches;
- domain omissions;
- incomplete interfaces;
- test gaps;
- evidence gaps;
- false completion claims.

## Discipline router

AutoDesign / AutoEngineer should activate only disciplines that materially affect the objective. Candidate domains include:

- systems engineering;
- software engineering;
- architecture and architectural technology;
- structural, civil, mechanical, electrical, environmental, industrial, manufacturing, and controls engineering;
- construction and skilled trades;
- materials science;
- physics and chemistry;
- mathematics, statistics, optimization, and operations research;
- cybersecurity and privacy;
- human factors, cognitive science, UX/UI, and accessibility;
- product management and business strategy;
- law, regulation, standards, ethics, and governance;
- scientific methodology and evidence evaluation.

Each activated discipline must contribute at least one concrete requirement, design decision, validation method, or failure mode.

## Professional boundary engine

Every project must classify work into:

- AI-safe conceptual work;
- technical drafting/specification work;
- externally verifiable factual work;
- work requiring qualified professional review;
- work requiring regulatory/authority approval;
- consequential actions requiring explicit owner authorization.

The package must identify where AI work stops and professional authority begins.

AutoDesign / AutoEngineer can support paid deliverables such as:

- professional-review handoff packages.

## Differentiation

The product is not positioned as “AI knows every profession.” Its differentiator is controlled synthesis:

1. route only necessary expertise;
2. convert prose to requirements;
3. expose assumptions and blockers;
4. distinguish design from engineering approval;
5. map requirements to tests/evidence;
6. end at a defined completion state instead of infinite iteration.

## Completion model

Permitted terminal states:

- CONCEPT COMPLETE
- SPECIFICATION COMPLETE
- IMPLEMENTATION READY
- IMPLEMENTED — VERIFICATION PENDING
- VERIFIED COMPLETE
- ACCEPTED COMPLETE
- PARTIALLY COMPLETE
- BLOCKED

The system must never promote itself to a higher state without corresponding evidence.
